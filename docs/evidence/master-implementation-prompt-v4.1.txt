# 3. THE THREE-PATH HYBRID AUGMENTATION MODEL

This section defines the mandatory V4.1 architecture.

## PATH A — MODEL-SELECTED COGNITIVE ASSISTANCE

**Priority: Primary**

**Default behavior: Available on demand to the model.**

The host model or agent decides whether a Cognition OS capability is relevant to its current assignment.

Use:

- Agent Skills.
- Skill metadata discovery.
- On-demand cognitive references.
- Host-supported tools.
- Optional MCP tool invocation.
- Supported agent delegation.

### Activation examples

When designing a software architecture, the model may select:

- First Principles.
- Systems Thinking.
- Inversion.
- Pre-Mortem.

When troubleshooting database corruption, the model may select:

- MECE.
- Kepner-Tregoe.
- 5 Whys.
- Hypothesis-Driven Analysis.

When evaluating a business decision, the model may select:

- Expected Value.
- Bayesian Updating.
- Cost-Benefit Analysis.
- Scenario Comparison.

### Primary activation rules

- Activation must be relevant to the task.
- Frameworks must provide identifiable incremental value.
- Avoid duplicate analysis already completed by the host.
- Do not load the entire framework registry.
- Do not automatically launch multiple specialist agents.
- Permit the host to complete simple tasks without cognitive augmentation.

### Invocation assurance

Model-selected skills are probabilistic in practice.

Do not claim that merely installing a skill guarantees its invocation.

Use carefully designed metadata, evaluation cases, and lightweight host guidance to improve selection reliability.

Preserve manual invocation as a diagnostic fallback, not as the primary user workflow.

---

## PATH B — EVENT-DRIVEN DETERMINISTIC CHECKS

**Priority: Secondary**

**Default behavior: Lightweight, selective, and controlled.**

Use host-supported lifecycle hooks for checks that benefit from deterministic triggering.

Potential examples:

- File validation after an edit.
- Schema checks after generating structured data.
- Detection of dangerous command arguments before execution.
- Secret leakage checks.
- Relevant test-result inspection.
- Static analysis of changed files.
- Lightweight context injection at subagent initialization.
- Validation of specified artifacts before delivery when a suitable event exists.

### Hook selection policy

Hooks must only be used when:

1. The event is officially supported.
2. The event payload provides sufficient information.
3. The check is narrowly scoped.
4. Processing overhead is acceptable.
5. Required permissions are granted.
6. Failure handling is defined.
7. The check does not duplicate another validator unnecessarily.

### Avoid unconditional LLM execution

Do not invoke an AI model at every hook event.

Prefer deterministic scripts for:

- File format validation.
- Schema checks.
- Static linting.
- Path validation.
- Policy checks.
- Structured artifact inspection.

A hook may provide actionable findings to the host agent where the host supports feedback injection.

Do not claim that all hooks can block, rewrite, or inject context.

### Hook failure policy

Distinguish:

**Advisory checks:** Graceful degradation when unavailable, with appropriate diagnostics.

**Security enforcement checks:** Follow verified host permission behavior; do not silently bypass a required policy.

### Event deduplication

Prevent repeated validation of unchanged artifacts.

Where practical, use:

- Content hashes.
- File-change filtering.
- Execution identifiers.
- Bounded result caching.
- Idempotent checks.

Avoid persistent background monitoring unless explicitly justified and authorized.

---

## PATH C — OPTIONAL DEEP COGNITIVE ADVISORY

**Priority: Conditional**

**Default behavior: Dormant unless justified.**

This path provides more comprehensive cognitive analysis when a task has meaningful complexity, uncertainty, or consequences.

It may activate:

- Multiple complementary mental models.
- Specialist advisory roles.
- Adversarial evaluation.
- Decision-theoretic analysis.
- Quantitative scenario simulation.
- Systems-level consequences.
- Detailed evidence validation.
- Independent artifact review.

### Activation conditions

Consider deep advisory when:

- The task involves substantial architectural trade-offs.
- The consequences of incorrect output are significant.
- Evidence is contradictory.
- The problem has multiple interacting causes.
- The task is unusually complex.
- Conventional analysis has failed.
- The user explicitly requests comprehensive analysis.
- The model identifies a critical uncertainty requiring investigation.

### Execution constraints

Deep advisory must:

- Respect user and host execution budgets.
- Use bounded iterations.
- Avoid spawning unnecessary agents.
- Use deterministic computation where appropriate.
- Return concise findings to the host.
- Preserve the host's authority.
- Require permission for costly or side-effecting operations.

Do not activate deep advisory merely because the user requests lengthy output.

Length and analytical complexity are different properties.

# 4. HYBRID ACTIVATION GOVERNOR

Implement an internal decision policy that coordinates the three augmentation paths.

## 4.1 Required inputs

Assess only accessible context, including:

- Current task objective.
- Task type.
- Risk.
- Complexity.
- Evidence sufficiency.
- Relevant artifacts.
- Available host capabilities.
- Available computational tools.
- Execution constraints.
- Context budget.
- Existing analysis.
- Potential duplication.
- Permission status.

## 4.2 Decision policy

Use this conceptual selection logic:

```text
Receive observable task context
    |
    v
Is cognitive augmentation relevant?
    |
    +-- NO --> PASS THROUGH
    |
    +-- YES --> Assess task complexity and risk
                    |
                    v
              Can a selected skill help?
                    |
                    +-- YES --> MODEL-SELECTED ASSISTANCE
                    |
                    v
              Is there an appropriate host event
              with a deterministic check?
                    |
                    +-- YES --> EVENT-DRIVEN VALIDATION
                    |
                    v
              Is deep analysis justified?
                    |
                    +-- YES --> DEEP ADVISORY
                    |
                    v
              Return relevant findings
                    |
                    v
              Continue original host task
```

The paths are not mutually exclusive.

A complex task may use model-selected skills, deterministic validation, and a targeted deep advisory review.

However, each additional path must have a justified purpose.

## 4.3 Operating policies

Provide:

`PASS_THROUGH`

No Cognition OS processing beyond unavoidable discovery overhead.

`LIGHT_AUGMENTATION`

One narrowly relevant capability.

`STANDARD_AUGMENTATION`

A compact sequence of complementary frameworks.

`DETERMINISTIC_VALIDATION`

A bounded tool or hook-based check.

`DEEP_ADVISORY`

Comprehensive analysis with specialized review.

`CRITICAL_REVIEW`

Heightened evidence and artifact validation for consequential tasks.

`DEGRADED`

Continue with supported capabilities when optional components are unavailable.

These are internal operating policies, not user-facing modes that must be manually selected.

## 4.4 Selection quality

Optimize for:

**Expected improvement in task quality relative to additional cost, latency, and interference risk.**

Do not invent a numerical optimization formula without defining measurable inputs.

Calibrate routing decisions using real evaluation results.
